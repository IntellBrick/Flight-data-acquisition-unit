# CANdleLight + CUAV GPS（DroneCAN）通讯测试诊断记录

日期：2026-09-14
参与设备：LC/bytewerk candleLight USB-CAN 适配器（`1D50:606F`，序列号 `003D002B4356510820333133`，CAN 时钟 48 MHz，能力位 `0x000000fb`）；雷迅（CUAV）GPS 模块（DroneCAN，状态灯绿灯常亮）；连接线长约 20 cm，**无终端电阻**。

## 1. 结论摘要

**当前无法建立通讯：从未收到过任何一帧有效的 DroneCAN 数据帧。**

已排除的原因：

| 项目 | 结论 | 依据 |
|---|---|---|
| USB/驱动/适配器硬件 | 正常 | 设备枚举正常、接受位速率配置、内部回环自发自收通过（5/5 帧回显） |
| 我方监听代码 | 正常 | 回环与真实接收路径均验证 |
| 波特率选择 | 已穷举标准值 | 1M / 800k / 500k / 250k / 125k / 100k 全部扫过，均为 0 帧 |
| 采样点差异 | 已排除 | 1M、500k 下 87.5% / 81.25% / 75% 采样点组合均 0 帧 |
| 偶发/间歇 | 已排除 | 累计约 10 分钟连续监听（含后台狩猎）无有效帧 |

## 2. 关键实测现象

1. **静止监听时总线完全无活动**：连续 5 个 5 秒窗口（1M/500k 交替），有效帧 0、错误帧 0。
2. **我方一旦发帧，立刻出现错误帧风暴**：1 Mbit/s 下发送 3 帧后 1 秒内收到 6657 个错误帧。
3. **我方发送的帧从未被正确应答**：正常模式下 TX 回显为 0（或带 `CAN_ERR_FLAG` 的失败回显），而回环模式下回显 5/5。

### 错误帧解码（来自 candleLight 固件 `src/can_common.c`，SocketCAN 风格）

| can_id 掩码 | 含义 | 实测次数（1 秒内） |
|---|---|---|
| `0x20000024` | ACK 错误（发出后无人应答） | 1357 |
| `0x2000000C` | CRTL + PROT（控制器状态 / 协议位错误） | 2238 |
| `0x2000004C` | 含 BUSOFF（控制器进入总线关闭） | 3062 |

即：适配器控制器在反复“发帧失败 → 协议/位错误 → bus-off → 自动恢复”的循环中。

## 3. 待区分的两个根因

### A. 物理层问题（首要怀疑）

- **未共地**：NEO 4SE 需独立 4.7–5.2 V 供电，而 CANdleLight 的 CAN 口**不输出 5V**。若 GPS 由独立电源供电而两边 GND 未相连，CAN 差分信号没有共同参考，会出现“模块自身正常但总线上完全测不到”的现象。
- **CAN_H / CAN_L 未按信号名对应**：两端连接器引脚顺序不同（见第 4 节），用一根 4P GH 排线直连会错位。
- **无终端电阻**：20 cm 短线在 1 Mbit/s 下通常仍可通讯，不是“完全静默”的主因，但会降低裕量，建议测试时在 H-L 间并一只 120 Ω。

### B. 模块工作在 CAN FD 模式（需确认）

雷迅 M4C GNSS 固件（NEO 4SE / NEO 4 Nano 同族）的默认参数为：

| 参数 | 默认值 | 说明 |
|---|---|---|
| `CAN_NODE_ID` | 0 | 0 = 由系统动态分配节点 ID |
| `CAN1_FD_EN_MODE` | 2 | Auto CANFD 模式 |
| `CAN1_FD_BITRATE` | 4 Mbps | FD 数据段速率 |
| `CAN_R` | False | 终端电阻默认关闭 |

**CANdleLight（经典 CAN 2.0B 控制器，能力位中 FD 位为 0）无法解码 CAN FD 帧。**若模块以 FD 帧发送，则经典适配器在任何经典波特率下都只能看到错误、看不到数据，与实测现象一致。该情形需要 CAN FD 适配器，或通过雷迅 LGC 地面站 / 支持 FD 的控制器把 `CAN1_FD_EN_MODE` 改为 0（关闭 FD）。

## 4. 接线核对清单（建议逐项用万用表确认）

1. **信号对应（按名称，不按引脚序号）**：适配器 CAN_H ↔ GPS CAN_H，适配器 CAN_L ↔ GPS CAN_L。
   - 雷迅 NEO 4SE：数据接口 `GHR-04V-S`（4P），按 DroneCAN 惯例为 5V / CAN_H / CAN_L / GND，**以模块丝印为准**。
   - LC CANdleLight：官方说明为 1 脚空（X）、2 脚 CAN_L、3 脚 GND，背面与 GND 对应为 CAN_SH（屏蔽），**以板子丝印为准**。
2. **共地**：GPS 供电电源的 GND 与适配器 GND 必须相连（通断档应导通）。
3. **供电**：GPS 连接器处实测 4.7–5.2 V。
4. **静态电平**：上电无通讯时，CAN_H、CAN_L 对 GND 均应约 2.5 V（若为 0 V 或悬空，说明收发器未工作或未接通）。
5. **终端电阻**：可临时在 H-L 之间并 120 Ω 后复测。
6. **对调试验**：把 H、L 对调后复测一次（这是软件侧无法区分的常见接反情形）。

## 2b. 稳态静默测量（决定性证据）

方法：不发送任何帧；每个波特率先丢弃 3 秒“稳定窗”，再测量 8 秒“稳态窗”，分别统计有效数据帧与错误帧。

| 波特率 | 稳定窗 | 稳态窗（8 s） |
|---|---|---|
| 1000 kbit/s | valid=0 err=0 | valid=0 err=0 |
| 500 kbit/s | valid=0 err=0 | valid=0 err=0 |
| 250 kbit/s | valid=0 err=0 | valid=0 err=0 |
| 125 kbit/s | valid=0 err=0 | valid=0 err=0 |

意义：若模块正在以**任意**与监听速率不同的速率发送（含 CAN FD 帧），本控制器会累积接收错误并触发控制器状态变化上报（本固件的错误帧机制），而实测为 0。因此结论是：

> **模块当前完全没有在 CAN 总线上驱动任何信号。问题不是“我们解不出来”，而是“总线上没有东西在发”。**

这使排查重点从“协议/FD 兼容性”转回“**物理连接**”：

1. **CAN_H / CAN_L 接反**：接反时两端互把对方的显性位看成隐性，表现为“双方都认为总线空闲”，与实测的完全静默高度吻合。
2. **未共地**：GPS 由独立电源供电而 GND 未与适配器相连时，接收端看不到有效差分电平。
3. **虚接 / 接错引脚**：线接在连接器其他引脚上，或压接不良。
4. 模块 CAN 收发器未工作（含模块处于异常固件状态）。

另：本适配器**不支持** `GS_USB_BREQ_BERR`(3) 与 `GS_USB_BREQ_GET_STATE`(14)（均返回 STALL），说明其固件版本早于上游新增这两个请求的版本，因此无法直接读取控制器状态与收发错误计数器，错误帧分析是当前可用的最佳手段。

## 2c. H/L 对调复测结果

断电对调 CAN_H / CAN_L 后重新上电、重新插拔适配器复测（`tools/can_quickcheck.py`）：

| 项目 | 结果 |
|---|---|
| 适配器枚举 | 正常（`1D50:606F`，序列号不变） |
| 回环自检 | PASS |
| 1000 / 500 / 250 kbit/s 稳态测量（各 7 s，不发帧） | 全部 valid=0、err=0 |

**结论：CAN_H / CAN_L 接反不是原因。** 总线依然完全静默，问题仍在供电/共地/连接通断或模块 CAN 侧。

## 2d. 换线后的当前快照（原始帧探针）

| 场景 | 观测 |
|---|---|
| 1M 监听 4 s（不发帧） | 0 帧（总线空闲） |
| 1M 发 3 帧后 1 s | 20 个错误帧 `0x2000000C`（CRTL+PROT），**我方帧回显带 ERR 标志** |
| 500k 监听 4 s（不发帧） | 3 帧，全部为**我方先前发送帧的失败回显**（`echo_id` 555/556/557，`can_id=0xABD00005` 带 ERR 标志） |
| 500k 发 3 帧后 1 s | 1 个错误帧 `0x20000024`（**ACK 错误**，无人应答） |

含义：我方发送的帧**从未被任何节点应答**，且总线在无人发送时完全空闲。即总线上没有能够接收并应答我们的对端。

## 7. 更换适配器后的重大进展（Makerbase CANable 2.0）

### 7.1 适配器对比结论

| 适配器 | 结果 |
|---|---|
| 旧 LC/bytewerk CANdleLight（gs_usb, `1D50:606F`） | 同一接线与供电下，1M/500k/250k 稳态监听**全部 0 帧**（回环自测 PASS，说明仅总线侧失效） |
| 新 Makerbase CANable 2.0（slcan, `16D0:117E`, COM10，固件 `16e7497-dirty github.com/normaldotcom/canable2.git`） | **立即收到数据**：1 Mbit/s 下稳定收到模块报文，500k/250k 下 0 帧 |

结论：**旧适配器的总线侧（收发器/时序）是此前“完全静默”的直接原因**；模块与接线本身没有问题。

### 7.2 模块的真实状态：等待 DroneCAN 动态节点 ID 分配

收到的报文（1 Mbit/s，优先级 12，源节点 ID = 0 即匿名）：

```
CAN ID 0x183F9900  数据 01 47 00 07 00 0A 51 <tid>    周期 ~0.8-1.0 s
CAN ID 0x18062500  数据 00 34 33 34 33 30 37 <tid>    （同一节点的第 2 段）
```

按 `uavcan/protocol/dynamic_node_id/1.Allocation.uavcan` 解析：

| 元素 | 解读 |
|---|---|
| 源节点 ID = 0 | **匿名**：该节点尚未获得节点 ID |
| CAN ID 位 23-8 = 0x3F99 / 0x0625 | **Discriminator**（随机数，规范允许每次传输变化，并非数据类型 ID） |
| 数据首字节 bit0 | `first_part_of_unique_id` 标志（该设备把它放在 bit0，而非常见位置 bit7） |
| unique_id 片段 | `47 00 07 00 0A 51` 与 `34 33 34 33 30 37`（ASCII “434307”，疑为序列号） |
| 周期 | 规范规定 `Trequest` = 600–1000 ms ✓ |

**即：模块运行正常、CAN 收发正常，但它处于“等待分配节点 ID”状态，因此不发布 NodeStatus(341) 与 gnss.Fix(1060)。** 这与该系列模块 `CAN_NODE_ID` 默认值 0（由系统自动分配）一致。

### 7.3 自建分配器的尝试与结果

按规范（含官方 allocator 伪代码）实现了 6 版分配器（`tools/dronecan_allocator*.py`）：

| 观察 | 意义 |
|---|---|
| 回显 6 字节后，模块**确实**发出第 2 段 `434307` | 模块能收到并接受我方报文，分阶段交换成立 |
| 已取得完整 12 字节 unique_id | `47 00 07 00 0A 51 34 33 34 33 30 37` |
| 以 12/16 字节 uid + `node_id`=1/125 反复授权（57 次，单帧与多帧均试） | **未被采纳**；模块继续请求，仍无 NodeStatus |

推测原因：该 M4C 固件的分配客户端可能要求**单帧内交付完整 unique_id**（16 字节只能由 **CAN FD** 帧承载——其默认 `CAN1_FD_EN_MODE=2`、`CAN1_FD_BITRATE=4 Mbps`），而经典 CAN 下 12/16 字节必须多帧，被其忽略。

### 7.4 建议的下一步

## 4b. 关于“打开适配器后 RX/TX 两灯同时常亮”的分析

现象：适配器被上位机打开（下发 `GS_CAN_MODE_START`）后，无论是否发帧，RX 与 TX 两个灯都同时常亮。

对照 candleLight 上游固件（`src/led.c`、`src/usbd_gs_can.c`、v1.0 版本 `led.c`）：

| 固件状态 | 触发条件 | 灯表现 |
|---|---|---|
| `LED_MODE_NORMAL` | `can_enable()` 通道启动 | **平时熄灭**，每收发一帧闪烁 45 ms（灭 30 ms） |
| `LED_MODE_OFF` | `can_disable()` 通道停止 | 两灯全灭 |
| `LED_MODE_SEQUENCE` | 仅主机下发 `GS_USB_BREQ_IDENTIFY` | RX 亮 100 ms → TX 亮 100 ms **交替**循环 |

结论：**“两灯同时常亮”在上游固件中不存在这种状态**，因此它不属于固件定义的“正常工作指示”，但也不构成故障证据。可能的解释（按可能性排序）：

1. **厂商自制固件把两灯用作“主机已连接 / 通道已启动”指示灯**——与该型号官方说明一致（“连接成功后 TX 和 RX 灯会亮起”）。此情形下该现象**不含总线信息**。
2. **LED 由收发器 TXD/RXD 电平直接驱动**（廉价克隆常见）：总线空闲（隐性）时两引脚均为高电平 → 两灯同时常亮；有帧时快速翻转，肉眼仍近似常亮。此情形下“两灯常亮”表示**总线处于隐性空闲电平**，属正常，反而排除了“总线被持续拉成显性（H/L 短路或节点卡死显性）”。
3. 若为固件驱动且把 bus-off 表示为常亮——与上游设计不符，且实测 bus-off 仅在**我方发帧**时出现，与“一打开就常亮、发不发都一样”不符。

判定实验：`tools/can_identify.py` 下发 `GS_USB_BREQ_IDENTIFY`。若两灯切换为 RX/TX 交替 100 ms 闪烁 → 灯由固件驱动（解释 1）；若完全无变化 → 灯为硬件电平驱动（解释 2）。两种情形都不改变主结论：现象本身不能证明 GPS 侧有问题。
